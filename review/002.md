# Architecture Review: Separating Library, CLI, TUI, and Site Generation

> **Scope**: Whole-repo structural review, 53,318 lines of Go across 19 packages
> **Baseline**: `go build ./...` ✅ `go vet ./...` ✅ `go test ./...` ✅ (all 19 packages green)
> **Date**: 2026-09-15
> **Question addressed**: should this be one library plus two applications, or two libraries plus two programs?

---

## Verdict

The instinct is right, and the target shape is:

**two libraries and three programs** — `podlib` (library management), `podsite` (feed/webpage
generation) as a thin consumer of `podlib`, and `pod` (CLI), `pod tui`, `pod offload` as
applications. The ad-removal pipeline is a *third* library that neither of the other two
should depend on.

But the diagnosis needs correcting first. The problem is **not** that the four concerns are
mixed into one package — they already live in separate packages, and the import graph is a
clean DAG with no cycles:

```
types ← util ← config ← backend ← audio/format ← pipeline ← podcast ← tui ← cli
```

The problem is that **the package boundaries are nominal, not real**. `pkg/podcast` is named
like a library but exports a flat bag of 281 symbols with no façade; `pkg/cli` is named like a
command router but contains roughly 8,000 lines of domain logic; `pkg/tui` bypasses the
library and reimplements pieces of it. Moving files will not fix this. Defining an API will.

---

## What is already right

Worth stating plainly, because the refactor should preserve all of it:

- **The dependency graph is acyclic and layered sensibly.** Nothing needs untangling in the
  cycle-breaking sense. This is the hard part, and it is already done.
- **`pkg/backend` has a real registry seam** (`backend.Register` / `backend.New`,
  `pkg/backend/backend.go:70-84`), and `pkg/tui` has a real injection seam (`TuiBackend`,
  `pkg/tui/tui.go:326`). Both are the right idea; both are under-used.
- **Sizing discipline is genuinely good.** No function over 80 lines, no file over 800.
- **Test coverage is respectable for a project of this shape** — 41% on `cli`, 48% on
  `podcast`, 66% on `tui`. A refactor of this size is only safe because these exist.
- **The pure-function core is already pure.** `ResolveEpisodesToDownload`, `PlanDownloads`,
  `MatchEpisodeDeduplication`, `FormatEpisodeFilename`, the feed/HTML generators — these take
  data and return data. That is the library, and it is already written.

## Finding 1 — The library has no façade, and the façade it has is dead code

`pkg/podcast` exports **281 symbols**. There is exactly one type that looks like an API
surface, `PodcastManager` (`pkg/podcast/manager.go:9`), with four methods. It is used
**nowhere outside its own file**:

```
$ grep -rn "PodcastManager" --include='*.go' pkg cmd main.go | grep -v manager.go
pkg/podcast/feed_cache.go:531:  feedUserAgent = "...ABSPodcastManager/1.0)"   # a user-agent string
```

Meanwhile `pkg/cli` reaches directly into **80 distinct `podcast.*` symbols** across 266 call
sites, and `pkg/tui` into 13 more. Every caller re-derives the wiring — build a
`SubscriptionStore`, build a `backend.Backend`, get the `DefaultFeedCache()`, resolve a
directory, call five free functions in the right order.

The most visible symptom: **seven different "find the podcast the user meant" functions**,
all exported, all subtly different.

|---|---|

## Finding 2 — The library prints

Direct `fmt.Print*` / `os.Stdout` writes in non-UI packages:

| Package | Writes | Package | Writes |
|---|---|---|---|
| `adremoval` | 105 | `transcribe` | 14 |
| `remote` | 66 | `util` | 14 |
| `pipeline` | 35 | `kitty` | 6 |
| `podcast` | 28 | `backend` | 5 |

**~278 hardcoded stdout writes below the UI layer.** `pkg/podcast` exports
`PrintAmbiguousMatches` and `PrintAuditSummary` — presentation functions in the library — and
`pkg/cli/execute.go:48` calls `PrintAmbiguousMatches` from its top-level error handler.

The consequence is not stylistic. It is that **the TUI cannot use these code paths at all**:
anything that prints to stdout corrupts the Bubbletea alt-screen. That is precisely why the
TUI reimplements the library instead of calling it (Finding 4). Fixing the printing is what
unblocks the deduplication.

The same leak runs through the `Backend` interface itself — see Finding 7.

## Finding 3 — `pkg/cli` is not a CLI

Line accounting for the 9,855 non-test lines in `pkg/cli`:

| | Lines |
|---|---|
| `clihelp` command/subcommand definitions (the actual CLI) | 1,817 |
| `handle*` / `run*` handlers | 2,055 |
| Everything else (helpers, DTOs, renderers, orchestration) | 5,983 |

**Only 18% of `pkg/cli` is command-line interface.** The rest is domain logic that a TUI, a
future daemon, or a test would want, and cannot have.

`pkg/cli/server_subscription.go` is the clearest case. In 615 lines it contains: feed
inspection, subscription store mutation, cover resolution, a **worker-pool download planner**
with its own goroutines and mutex (`planSubDownloads:305`), download execution, RSS
generation, catalog webpage generation — and `fmt.Printf` interleaved through all of it.

`handleServerFeed` (`:173`) is 40 lines that do five different jobs: resolve targets, write
feed XML, opportunistically backfill a missing `ImageURL` into the store and re-save it, count
episodes, and write the catalog page. The store mutation buried at `:198` is a library
operation hiding inside a print loop.

## Finding 4 — The TUI bypasses the library and reimplements it

`RunTUI` receives `cfg *types.Config` — and then **seven call sites reload the config from
disk anyway**, ignoring the one they were handed:

```
pkg/tui/tui_modal_download.go:240    pkg/tui/tui_batch.go:135
pkg/tui/tui_feed_fetch.go:30         pkg/tui/tui_batch.go:199
pkg/tui/tui_feed_fetch.go:199        pkg/tui/tui_latest_view.go:245
pkg/tui/tui_keys_queue.go:159
```

Each then constructs its own `backend.FromAppConfig(cfg, true)`. The `TuiBackend` injection
seam covers four operations; every other data access routes around it.

Worse, the TUI reimplements domain logic that already exists in the library. Episode
deduplication is `podcast.MatchEpisodeDeduplication(guid1, enc1, title1, ...)`
(`pkg/podcast/queue.go:156`). The TUI does not call it — it open-codes its own version at
`pkg/tui/tui_feed_fetch.go:45-53` against a locally built triple-index of titles, GUIDs and
URLs. Two implementations of "is this the same episode" will drift, and only one has tests.

And `tui_batch.go` builds the same 10-field `podcast.DownloadQueueItem` twice, 60 lines apart
(`:121` and `:180`), with the same GUID/pubdate fallback chain copy-pasted.

Distinct structs representing an episode, excluding test fixtures:

| `podcast.LocalEpisodeMeta` | `podcast/feed_generator.go:74` | library |
| `podcast.ResolvedEpisode` | `podcast/id_registry.go:35` | library |
| `types.EpisodeStatusFile` | `types/episode.go:34` | pipeline |
| `tui.tuiEpisode` | `tui/tui_types.go:51` | TUI |
| `tui.EpisodeOnlineRelease` | `tui/tui_timeline_view.go:15` | TUI |
| `cli.lsEpisodeItem` | `cli/info_list.go:30` | CLI |
| `cli.lsEpisodeJSON` | `cli/info_list.go:46` | CLI |

Fifteen. Some are legitimate — a JSON DTO should be a separate type from a domain entity, and
`FeedEpisode` (remote, from RSS) genuinely differs from a downloaded local episode. But the
middle five — `CachedEpisodeSummary`, `CachedEpisodeDetails`, `LocalEpisodeMeta`,
`ResolvedEpisode`, `tuiEpisode` — are five views of the same thing: *an episode that exists on
disk*. Conversion between them is hand-written, lossy, and scattered.

**A library needs one domain `Episode`.** Serialization shapes (cache file, feed item, JSON
output) hang off it; they do not replace it.

## Finding 6 — `Config` and `CLIOptions` cross every boundary

Flattened field counts, measured via reflection:

- **`types.Config`: 48 fields**
- **`types.CLIOptions`: 100 fields**

`Config` mixes, in one struct: library settings (`PodcastsDir`, `ServerBaseURL`,
`SubscriptionsFile`), transcription settings (14 Whisper fields), LLM settings, Gemini
settings, remote-cluster settings, download policy — and **`TUIColor *TUIColorConfig`**
(`types/types.go:299`).

The library's configuration object carries the terminal UI's color scheme. That single field
is the whole problem in miniature: there is no config type that describes "what a podcast
library needs to know," so everything that needs any setting takes the one that has all of
them.

`CLIOptions` is passed **by value** through 285 call sites in `pkg/cli`. It embeds
`ProcOptions`, `RemoteOptions`, `PolicyOptions` and `BackendOptions`, so `handleServerAdd` —
which needs a feed URL and a quiet flag — receives a 100-field struct including
`WhisperGreedy` and `ShowExamples`. Every handler signature is `(cfg Config, cli CLIOptions)`,
which means every handler's true dependencies are invisible.

## Finding 7 — `Backend` is shaped by a backend that is no longer used

`backend.Backend` (`backend/backend.go:44`) is **30 methods** across three sub-interfaces. It
was shaped by the PodFetch HTTP API. `architecture.md` states PodFetch now exists only as a
one-time read-only OPML import source — yet the interface still demands the full surface from
everyone.

On `StandaloneBackend`, the primary and effectively only backend, **eight methods are pure
no-ops**:

```go
func (b *StandaloneBackend) ActiveDownloads(id string) ([]backend.ActiveDownload, error) { return nil, nil }
func (b *StandaloneBackend) ResetPodcastDateCheck(itemID, title string) error            { return nil }
func (b *StandaloneBackend) ResetPodcastDateCheckAPI(itemID string) error                { return nil }
func (b *StandaloneBackend) SyncDuration(filePath string, d float64) error               { return nil }
func (b *StandaloneBackend) TestConnection(quiet bool) (bool, error)                     { return true, nil }
func (b *StandaloneBackend) Login() (string, error)                                      { return "local", nil }
func (b *StandaloneBackend) Scan(opts backend.ScanOptions) (backend.ScanResult, error)   { return backend.ScanResult{}, nil }
func (b *StandaloneBackend) Rescan(...) (backend.RescanResult, error)                    { return backend.RescanResult{}, nil }
```

And the interface itself leaks presentation into the domain contract:

```go
ApplyKeepPolicy(podcastID, podcastTitle string, keep int, dryRun, verbose, quiet bool) (int, error)
TestConnection(quiet bool) (bool, error)
FetchPodcastFeeds(silent, verbose bool) ([]OPMLFeed, error)
WaitForActiveDownloads(podcasts []Podcast, quiet bool, timeout time.Duration) error
```

`quiet`, `verbose` and `silent` are **UI concerns encoded in the library's central
abstraction**. Any implementation is obliged to know how loud to be. This is the root cause of
Finding 2: the library prints because the interface tells it to.

There is also a layering inversion worth naming: `pkg/podcast` imports `pkg/backend` *and*
registers the primary implementation of `backend.Backend` back into it
(`standalone_backend.go:25-34`). The abstraction sits below its only real implementation.
Go permits this, but it means `pkg/backend` cannot be understood without reading
`pkg/podcast`.

## Finding 8 — Site generation is invoked from four layers, and hides a side effect

`WritePodcastFeedXML` / `WriteCatalogWebpage` / `WritePodcastWebpage` are called from:

- `pkg/cli/server_subscription.go` — 6 sites
- `pkg/podcast/standalone_backend.go` — 4 sites (inside `DownloadEpisodes`)
- `pkg/adremoval/rm_ads_podcast.go:566` — 1 site, after an ad-removal cut

There is **no single "republish the site" entry point**. Whether the feed gets regenerated
depends on which code path happened to touch the podcast.

And the two generators are secretly coupled — writing a feed silently also writes a webpage:

```go
// pkg/podcast/feed_generator.go:375
func WritePodcastFeedXML(podDir string, sub Subscription, baseURL string, feedEpisodes []backend.FeedEpisode) error {
    ...
    data, err := GeneratePodcastFeedXML(sub, podDir, episodes, baseURL)
    ...
    _ = WritePodcastWebpage(podDir, sub, baseURL, feedEpisodes)   // :397 — undeclared, error discarded
}
```

The good news: this concern is **the cleanest extraction in the codebase**. `feed_generator.go`
(407) + `webpage_generator.go` (255) are ~660 lines, both already built around pure
`Generate*HTML`/`Generate*XML` functions that take data and return bytes. The `Write*`
wrappers are the only part entangled with the filesystem and the store. Splitting the pure
generators from the publish orchestration is a half-day job with existing test coverage
(`feed_generator_test.go`, `webpage_generator_test.go`).

Also note the ~4KB of CSS embedded as a Go string constant at `webpage_generator.go:16`. That
belongs in `//go:embed` assets.

## Finding 9 — Process-global mutable state

A library must be safe to instantiate twice. These are not:

| Global | Location |
|---|---|
| `globalFeedCache` + `DefaultFeedCache()` | `podcast/feed_cache.go:116` |
| `globalDownloadQueue` + `DefaultDownloadQueue()` | `podcast/queue.go:85` |

| `testConfigPath` | `config/paths.go:17` |

`DefaultDownloadQueue()` is called directly from TUI keystroke handlers
(`tui_batch.go:133, 190`). The queue — a core piece of library state — is reached through a

## Finding 10 — Three entrypoints, two of them dead

```
main.go           → embeds VERSION, calls cli.Execute      ← the real one (tools/build_local runs `go build .`)
cmd/pod/main.go   → calls cli.Execute                      ← dead
cmd/abs/main.go   → calls cli.Execute                      ← dead
```

`cmd/pod` and `cmd/abs` are byte-identical to each other and lack the `//go:embed VERSION`
that the root `main.go` has — so if either were ever built, `pod --version` would fall through
to the hardcoded string `"0.2.72"` at `pkg/cli/app.go:29`. They should be deleted, or become
the real entrypoints once there is more than one binary.

Related dead weight: `preparePublicationSource(action, appCfg, cli)` (`pkg/cli/publication.go:8`)
takes three arguments, ignores all of them, and always returns `nil` — and `Execute` branches
on its error at `execute.go:26`.

And `pkg/util/sync.go` wraps `sync.Mutex`/`sync.WaitGroup`/`sync.RWMutex` in identically-shaped
named types that add nothing. AGENTS.md mandates this ("no sync package"), but the wrapper
provides no behavior — it only makes `go vet`'s copylock analysis and standard Go idiom harder
to apply.

## Proposed structure

```
pkg/podlib/            LIBRARY 1 — managing a podcast library. No printing. No globals.
  library.go             Library façade: Open(Config) *Library
  episode.go             ONE domain Episode + ONE Podcast
  resolve.go             ONE Resolve(query) (Target, error)   ← replaces 9 matchers
  subscription.go        store
  feed/                  RSS fetch, conditional GET, cache
  download/              plan + execute (returns progress on a channel, prints nothing)
  index/                 on-disk scan, cache, short IDs
  config.go              PodcastsDir, ServerBaseURL, SubscriptionsFile — and nothing else

pkg/podsite/           LIBRARY 2 — static feed/webpage generation. Depends on podlib only.
  rss.go                 Generate(Podcast, []Episode) ([]byte, error)
  page.go                Generate(...) ([]byte, error)
  publish.go             Publish(*podlib.Library, Options) — the ONE republish entry point
  assets/                //go:embed CSS

pkg/proclib/           LIBRARY 3 — ad removal. Depends on podlib; podlib must NOT depend on it.
  (today: pipeline + adremoval + transcribe + detect + gemini + audio + remote)

pkg/cli/               APP 1 — clihelp wiring, flag parsing, table/JSON rendering. ~2,500 lines.
pkg/tui/               APP 2 — Bubbletea. Talks to podlib through one interface. No LoadConfig.
pkg/offload/           APP 3 — remote worker daemon (today buried in pkg/cli).

cmd/pod/main.go        the single entrypoint
```

**Answering the question directly:** two libraries rather than one, because `podsite` has a
genuinely different lifecycle — it is pure rendering, it is the thing most likely to be
replaced (different templates, a different static-site generator), and it is the easiest piece
to extract. `procl`/ad-removal is a third library and the most important dependency rule in
the whole design: **`podlib` must not import it.** Today `pkg/podcast` imports `pkg/pipeline`
at 21 call sites (`audit.go`, `cache.go`, `feed_generator.go`, `id_registry.go`, `queue.go`,
`priority.go`, `standalone_backend.go`) — which means "list my episodes" drags in the
transcription pipeline. That inversion is what keeps the library from being liftable.

## Migration path

Ordered by ratio of benefit to risk. Each step compiles, tests, and ships on its own.

### Progress

- **Finding 1's second half, done.** The façade landed in Step 4, but the
  surface behind it did not shrink: `pkg/podcast` still exported 109 functions,
  and 49 of them were internal detail leaking out.
  - 109 functions across six packages are now unexported — every one that
    nothing outside its own package called. The compiler verified each: an
    unexport that broke a caller would not build, and the first build was clean.
  - **Exported surface: `podcast` 109 → 61, `util` 46 → 31, `config` 45 → 30,
    `pipeline` 50 → 37, `backend` 22 → 15, `format` 20 → 9.** One
    internal-only export remains, skipped because unexporting it would collide
    with an existing name.
  - **The point was not the rename.** Staticcheck's U1000 only reports
    *unexported* dead code, so none of this was visible to it before. The
    moment it was, the linter found **19 dead declarations by itself** — and
    kept finding them: `acquireWorkerLock`, `releaseWorkerLockFunc`,
    `acquireCollectLock` and their shared lock table are offload-era code that
    the 0.3.0 removal missed, still carrying the error string "remote worker is
    already running".
  - A further six functions were alive only because their own tests called
    them. Two were mine, left behind in Step 1 when `PublishPodcast` started
    calling `podsite` directly. `buildOPMLXML` was a second OPML builder,
    superseded when `ExportOPML` moved to `store.ExportToOPML`. Each was
    deleted with its test, after checking the coverage existed elsewhere —
    `podsite`'s goldens already cover the two renderers.
  - Net: **−506 lines**, and dead code now surfaces on its own from here.
  - `podsite` and `progress` measured zero internal-only exports before and
    after. Their surfaces were already exactly what callers use.

- **Step 7 superseded: the remote/offload feature was removed at the user's
  request rather than extracted.** The step called for lifting `pkg/offload`
  out of `pkg/cli`; the feature is no longer needed, so it is gone instead.
  - Deleted: `pkg/remote` (2,669 lines), `pkg/cli/offload*.go` (544), the
    remote branches in the ad-removal batch path, `types.RemoteConfig` and
    `types.RemoteOptions`, the `--remote` / `--local` / `--remote-host` /
    `--rffmpeg` / `--no-collect` flags, the `rm_ads collect` and `rm_ads
    clear` subcommands, the four `remote_*` config keys and their environment
    overrides, and `tools/verify_remote_queue` / `tools/setup_remote_worker`.
    Roughly 3,900 lines in total; the top-level command count went from 8 to 7.
  - **Kept deliberately:** the remote *episode states* (`StateQueuedRemote`,
    `StateTranscribingRemotely`, `StateCuttingRemotely`,
    `StateReadyForCopyBack`, `StateCopiedBack`) and the code that reads them.
    Status files already on disk carry those values, and deleting the
    constants would misread them. `pod rm_ads --dry-run` now reports such
    episodes as "Stranded in a remote state" so they stay visible rather than
    silently uncounted.
  - Also kept: `WhisperEngineRemote`, which is an HTTP whisper server and has
    nothing to do with the offload cluster despite the name.
  - `--rffmpeg` turned out never to have run ffmpeg remotely — `pkg/audio` has
    no SSH at all. It was only another way to name the offload host, so it
    went with the rest rather than surviving as a separate feature.
  - The pre-deletion state is tagged `pre-remote-removal`. Git is the archive;
    recovering the package is one `git checkout` away.

- **Step 0 — done** (`a0f7baa`).
- **Step 1 — done.** `pkg/podsite` extracted as a pure renderer (473 lines) importing
  only `pkg/format`; `podcast.PublishPodcast` / `PublishCatalog` are now the single
  write entry points. Verified byte-identical output against pre-refactor goldens
  covering XML/HTML escaping, unicode filenames, URL escaping, the remote-image
  fallback, the report link, the OPML link, catalog sorting, and the empty-baseURL
  variants. Golden files now live in `pkg/podsite/testdata` and are checked on
  every run (`go test ./pkg/podsite -update` to regenerate).
  - One deviation from the plan below: `podsite` imports **nothing** from the
    podcast library rather than depending on it. Making it a pure renderer avoided
    an import cycle (`podcast.StandaloneBackend` publishes after downloading) and
    is a stronger boundary than originally proposed. The orchestration that reads
    the filesystem stays in `pkg/podcast/publish.go` until Step 5 moves it into
    `podlib`.
  - Two real defects fell out of the extraction: `index.html` was being written
    **twice** on every download and every episode delete (the hidden side effect at
    the old `feed_generator.go:397` plus an explicit second call), and
    `GenerateCatalogWebpageHTML` took a `baseURL` parameter it never used. Both
    fixed.
  - Left deliberately unchanged: the feed honours the `SERVER_BASE_URL`
    environment fallback but the HTML page does not. That asymmetry predates this
    work and looks like a bug; changing it is a behaviour change, not a
    refactor, so it is called out here rather than folded in silently.

- **Step 2 — done.** `pkg/podcast`, `pkg/backend` and `pkg/podsite` now make
  **zero** direct writes to stdout or stderr, down from 33. `pkg/progress`
  carries output out of them instead, and a nil `Reporter` is silent, so no
  caller threads a quiet flag.
  - The `Backend` interface lost every presentation flag:
    `ApplyKeepPolicy(..., dryRun, verbose, quiet)` → `(..., dryRun)`,
    `FetchPodcastFeeds(silent, verbose)` → `()`,
    `WaitForActiveDownloads(podcasts, quiet, timeout)` → `(podcasts, timeout)`,
    and `TestConnection(quiet)` → `TestConnection(progress.Reporter)`. Only the
    last actually used its flag; the other six were dead in every
    implementation. `backend.Config.Quiet`/`.Verbose` and the identical dead
    fields on `PodFetchBackend` are gone too.
  - **A live bug is fixed.** The TUI called `pipeline.PrintQuarantinedSummary`,
    which wrote to stdout from under the Bubbletea alt-screen and corrupted the
    display. It is now `FormatQuarantinedSummary`, returning text the model
    surfaces as a toast. This was Finding 2's predicted failure, found in
    production code rather than in theory.
  - **`pkg/podcast/audit.go` was deleted outright** — 203 lines and 15 of the
    28 prints. It duplicated `pkg/adremoval/rmads_audit.go`'s unexported
    implementation function for function, down to a second copy of
    `AuditDisplayName`, and nothing called it. `PodcastManager.AuditTranscripts`
    went with it.
  - The boundary is now enforced, not just documented:
    `TestLibraryPackagesDoNotWriteToTheTerminal` fails the build on a new
    `fmt.Print*`, bare `println`, or `os.Stdout`/`os.Stderr` in a silent
    package. Verified against all three leak shapes.
  - Scope held to what this step named. `pkg/pipeline/pipeline.go` (29 prints),
    `pkg/adremoval` (105) and `pkg/remote` (66) still print. They are the
    ad-removal processing path — `proclib` in the target structure — and none
    of them sits between the TUI and the library, which is what Step 2 existed
    to unblock. Only `quarantine.go` did, and it is fixed.
  - **Found, not fixed:** `pod server download --dry-run --quiet` prints ~11 KB
    to stdout. The leak is in `pkg/cli/server_subscription.go:462` and `:475`,
    which never check `cli.Quiet`. Byte-for-byte identical before and after this
    step, so it predates it. It belongs to Step 5.

- **Step 3 — done, with the plan corrected.** Two commits: query resolution,
  then the episode types.
  - **Resolution.** `ResolvePodcastDirByIDOrName` was dead. The two group
    resolvers were the same 35 lines twice, differing only in element type and
    a field name, down to identical labels — now one generic `filterGroup`. The
    two podcast matchers shared a fuzzy-name phase and an ambiguity path — now
    one generic `matchByName`. The CLI's copy-pasted inline subscription match
    is now `podcast.SubscriptionMatches`.
  - **What did not collapse, deliberately:** the ID fallbacks inside the local
    and backend matchers. They look alike but differ in ways that decide which
    podcast a query selects — local compares folder names case-insensitively
    and tries a numeric index before an exact folder match; backend compares
    opaque server IDs case-sensitively and tries a short-ID-of-title first.
    Merging them would have changed behaviour while looking like a cleanup.
  - **Finding 5 was overstated and is corrected here.** The claim was that five
    episode types are "five views of the same thing" and should collapse into
    one. Reading the fields, they are not. The core common to all five is three
    strings (path, filename, title); the union is about thirty fields. A single
    `Episode` would have been a god struct in which most fields are meaningless
    for most callers — worse than what was there. What was real is that the
    shared core was *restated* five times, so the same concept had five field
    names (`Duration` vs `DurationSec`, `FileSize` vs `SizeBytes`).
  - **What was done instead:** `podcast.EpisodeFile` defines the six fields that
    every downloaded-episode representation agrees on, once, with one set of
    JSON tags. `CachedEpisodeSummary` and `LocalEpisodeMeta` embed it.
    `CachedEpisodeDetails` and `ResolvedEpisode` do not — they share only the
    identity triple, and seven composite-literal rewrites to hoist three
    strings is not worth it.
  - **Dead persisted state removed:** `CachedEpisodeSummary.Favorite` was never
    written and never read; every `Favorite` in the codebase belongs to
    `PodcastConfig` or `EpisodeStatusFile`. `ID` looked equally dead — nothing
    writes it — but the compiler caught `episodeShortID` reading it as a
    fallback for caches written by older versions of pod. It stays, now
    documented. That is the difference between deleting on a grep and deleting
    on a type check.
  - **The asymmetric cache round-trip is now pinned.** The TUI writes ten fields
    into the cache and restores six; `fileSize`, `hasAdsRemoved`, `path` and
    `filename` are deliberately recomputed from the filesystem instead. That was
    undocumented and indistinguishable from a bug. Two tests in `pkg/tui` now
    state which fields survive a restart and which are recomputed.
  - Verified three ways: a 270-line resolution table captured before any edit
    and byte-identical after (now `pkg/podcast/testdata/match.txt`); the cache
    JSON wire format byte-identical (now `pkg/podcast/testdata/cache_*.json`);
    and, end to end, all 84 feeds, 84 pages and the catalog regenerated from the
    real library byte-identical against a binary built from the previous commit.

- **Step 4 — done, with one part of the plan dropped as wrong.**
  - `podcast.Library` replaces the vestigial `PodcastManager`. It owns the
    config, the backend, the feed cache, the download queue and the reporter,
    and carries the operations that need library-wide state.
  - **`podcast.Config` is three fields** — `PodcastsDir`, `SubscriptionsFile`,
    `ServerBaseURL` — exactly what the library was measured to read from the
    48-field `types.Config`. `pkg/podcast` no longer references `types.Config`
    anywhere, and a test fails the build if it starts to. The last holdout was
    `ResolveEpisodesToDownload`, which synthesised a whole `types.Config` to
    carry two policy values; `config.PolicyDefaults` now carries them directly.
  - **The singletons are gone from the API.** `DefaultFeedCache` and
    `DefaultDownloadQueue` are unexported. Nothing outside `pkg/podcast` can
    reach process-global library state any more; the TUI holds a `Library` on
    its model and the CLI builds one per command. That is Finding 9 fixed at
    the boundary.
  - They are still one shared instance per process behind the façade, and that
    is deliberate rather than unfinished: each serialises one file through its
    own mutex, so two instances over the same path would serialise against
    different mutexes and race on it. A test states this.
  - **"Convert pkg/cli's 266 direct `podcast.*` calls to method calls" was
    dropped.** Measured, only 19 of the library's 161 exported functions take
    library-wide state; the rest take an explicit `podDir` or are pure helpers
    like filename formatting and feed parsing. Routing those through a receiver
    would make pure functions look stateful and churn hundreds of call sites to
    make the code worse. The façade covers the stateful surface, which is the
    part that needed it.
  - Verified end to end: 253 generated files byte-identical against a binary
    built from the previous commit.

- **Step 5 — first slice done** (the subscription download run). The step as
  scoped is about a week's work across five files; this commit takes the one
  the review named as its flagship example and leaves the rest.
  - `pkg/cli/server_subscription.go` is 618 → 383 lines. The goroutine worker
    pool, the feed fetching, the episode-selection policy cascade, the
    download execution and the republish are now
    `pkg/podcast/subscription_download.go`, reached through `Library`.
  - The handler is now parse → call → render: it builds
    `SubscriptionDownloadOptions` from the flags, calls
    `PlanSubscriptionDownloads` with a progress callback for the in-place
    counter, renders the report, and calls `ExecuteSubscriptionDownloads`.
    The `\r` spinner stays in the CLI, which is where a spinner belongs.
  - **The `--quiet` leak from Step 2 is fixed.** `pod server download
    --dry-run --quiet` printed ~11 KB to stdout because `printDryRunPlans`
    never checked the flag. It now prints nothing; the non-quiet path is
    unchanged.
  - Five tests moved from `pkg/cli` to `pkg/podcast` alongside the logic they
    cover, and now exercise the library API rather than a command's flag
    struct. Two gained assertions the CLI versions could not make: that the
    progress callback fires once per feed, and that a plan with nothing to
    download still republishes the podcast.
  - Remaining for Step 5 after the queue slice: `server_policy.go` (494),
    `server_frequency.go` (347), `server_download.go` (272), and the
    `CLIOptions` split.

- **Step 6 — done, and it found a real bug.**
  - **The TUI no longer reads config or builds backends on its own.** Seven
    `config.LoadConfig()` calls and eight `backend.FromAppConfig` constructions
    are now one of each, in `RunTUI`. The model holds the config it was
    launched with and reaches the backend through `Library.Backend()`. A
    full-screen session should act on the configuration it started with, not
    on whatever the file happens to say mid-run.
  - **Four copies of the download-queue item construction had drifted, and one
    was broken.** The Latest Episodes screen's copy omitted `EnclosureURL` and
    the GUID fallback. An episode queued from there reached the worker with no
    URL; `StandaloneBackend.DownloadEpisodes` skips an episode with no
    enclosure *and returns no error*, so the queue marked it completed and the
    episode was never downloaded — silently. Confirmed with a failing test
    before the fix, and the four copies are now one
    `downloadQueueItemFor`. This is Finding 4's prediction landing in
    production code: two implementations drift, and only one is tested.
  - **The dedup logic was left alone, deliberately.** The review called for
    replacing the TUI's index-based dedup with
    `podcast.MatchEpisodeDeduplication`. They are not equivalent: the library
    version compares case-insensitively and normalises titles through
    `NormalizeEpisodeTitle` (which strips a trailing GUID), so swapping would
    change which episodes count as duplicates. It is also pairwise where the
    TUI builds an index — O(n·m) against O(n+m) for a bulk feed comparison.
    Two different jobs, not one duplicated.
  - Verified with the 19-screen live PTY visual audit (`make visual`) in
    addition to the test suite.
  - One test-hygiene fix along the way: the new regression test triggered the
    download worker, whose goroutine outlived it and wrote a lock file into
    `pkg/tui/`. It now waits for the worker before releasing the queue path.

- **Step 5 — `CLIOptions` slice done, and the plan corrected by measurement.**
  - The review called for splitting `CLIOptions` per command group. Measuring
    which fields are actually read says that is the wrong fix: of ~271 reads,
    **144 are four flags** — `Quiet` (87), `Verbose` (24), `DryRun` (19),
    `JSON` (14) — and 71 more are `Args`. The remaining 96 fields are a long
    tail, mostly one command each. Splitting per command would duplicate those
    four flags into every resulting struct, which is worse than what is there.
  - The dominant coupling is not the field count, it is 43 hand-written
    `if !cli.Quiet` guards around printing. That is the CLI re-implementing,
    once per call site, what `progress.Reporter` already does for library
    calls — and a forgotten guard is exactly the `--quiet` leak found in
    Step 2.
  - `outFor(cli)` returns stdout, or `io.Discard` under `--quiet`. 33 of the 43
    guards are now unguarded `fmt.Fprintf(outFor(cli), ...)` calls: quiet is a
    property of the writer, so it cannot be forgotten. The other 10 keep an
    explicit guard because their blocks do more than print — a spinner that
    also calls `os.Stdout.Sync()`, a closure assignment, stderr writes.
  - Byte-for-byte identical across 24 command runs — twelve commands each in
    quiet and non-quiet mode, 739 lines of output — against a binary built
    from the previous commit. Every argument in the converted calls was
    checked to be side-effect free, since a discarded `Fprintf` still
    evaluates them.
  - What remains of the original `CLIOptions` idea is the long tail, and the
    right treatment is the one already used four times in this step: give a
    handler's callee a narrow options struct (`PolicyUpdate`,
    `SubscriptionDownloadOptions`, `FrequencyOptions`) rather than splitting
    the parse target that `clihelp` fills.

- **Step 5 — fourth slice done** (frequency analysis and backend target
  selection). `pkg/cli/server_frequency.go` is 347 → 283 lines.
  - `processSingleFrequencyItem` — cadence analysis, locating or creating the
    podcast directory, recording the result, and the hourly-disable rewrite —
    is now `Library.AnalyzeFrequencies`.
  - **A second hidden config read, fixed.** `filterServerTargets` called
    `loadConfig()` to get the library root, re-reading
    `~/.config/pod/config.json` from inside a filter whose caller already held
    the config. It is now `Library.SelectBackendTargets`. Same pattern as the
    policy sync in the previous slice; worth noting that reading the config
    from disk in passing had become a habit in this package rather than a
    one-off.
  - `PathSafeTitle` names the character replacement that turns a podcast title
    into a directory name. It was an anonymous `strings.Map` inline in the
    handler, and it is easy to mistake for `SanitizeTitle` — which strips a
    title to letters and digits and would produce a different directory
    entirely. A test asserts the two disagree.
  - **`server_download.go` needs no extraction and was left alone.** The review
    listed it, but reading it, it is already parse → call → render over
    `podcast.PlanDownloads` and `ExecuteEpisodeDownloads`; what remains is
    progress rendering and `runPostProcessors`, which shells out to
    user-configured commands with stdout wired to the terminal. That is a CLI
    concern. (`runPostProcessors` discarding every processor's exit status was
    noted here and has since been fixed — see below.)
  - Verified by replaying `server frequency`, `--verbose`, `disable-hourly`,
    and `server download --dry-run` (plus its `--quiet` byte count) against a
    binary built from the previous commit. 370 lines of output, identical.

- **Step 5 — third slice done** (podcast policy). `pkg/cli/server_policy.go`
  is 494 → 436 lines; the policy domain is `pkg/podcast/podcast_policy.go`.
  - `podcast.PolicyUpdate` replaces `CLIOptions` in the mutation path. This is
    the first real piece of the `CLIOptions` split: `ApplyPolicyUpdate` takes
    seven named fields instead of a 100-field struct, and "did the user ask to
    change anything?" is now `update.IsEmpty()` rather than a hand-written
    `checkHasPolicyUpdates` listing the same fields a second time.
  - **Group updates rebuilt the backend once per podcast.**
    `syncPolicyWithBackend` called `loadConfig()` and `backend.FromAppConfig`
    on every iteration, so `pod server policy --all` re-read
    `~/.config/pod/config.json` once per podcast — 80 times on this library.
    `Library.SetGroupPolicy` uses the one backend the Library already holds.
    Honest note: this is a structural fix, not a speed-up. Measured on 80
    podcasts the difference is inside the noise (23 ms vs 28 ms), because
    constructing the standalone backend is cheap and the OS caches the config
    file.
  - Message formatting stayed in the CLI. The library returns a typed
    `BackendSync{Backend, Err}`; the two different wordings the two code paths
    use ("Connected to X" when displaying, "Synced to X" when updating) are
    rendered by the command, so the library holds no user-facing strings.
  - **Surfaced, not changed:** `--favorite true` does not set one flag. Through
    `PodcastConfig.SetFavorite` it also switches auto-download on, ad removal
    to `all`, and the download policy to `new`. A user who marks a podcast
    favourite after configuring a download policy will find the policy
    replaced. That is long-standing behaviour and is now stated in a test
    rather than left to be discovered.
  - Verified by replaying eleven policy scenarios — single and group, set and
    show, `--json` for both, favourites, non-favourites, and the
    `none`-disables-auto-download interaction — against a binary built from the
    previous commit. Output identical.

## One process observation

AGENTS.md is unusually disciplined, and its caution about physical file splits is well
earned — the two incidents it cites (`c9b68f4`, `1c49c7b`) are real and the reasoning is
sound. Two of its rules, though, are contributing to the condition being reviewed:

- **"No comments in code."** In a codebase with nine podcast matchers and fifteen episode
  types, the thing a reader most needs is the one sentence saying which to use. The rule
  optimizes for self-documenting function bodies and gives up the ability to document
  *boundaries*. A package-level doc comment on each of the proposed libraries would be worth
  more than any refactor in this document.

- **The 80-line function limit applied without a module-boundary counterweight.** It is a good
  rule, and it has kept every function readable. But `pkg/cli` is now 83 files, and
  decomposition-in-place with no corresponding pressure to *extract packages* produces exactly
  what is here: many small, well-formed functions with no architecture between them. The limit
  is worth keeping; it needs a companion rule about what belongs in which package.

Neither rule caused the coupling. But a codebase that forbids explaining itself and rewards
splitting functions over splitting responsibilities will keep regenerating this shape.
