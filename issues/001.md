# 001 — Podcast config defaults outside the ad-removal engine

Both issues were found while fixing the podfetch episode-discovery bug in
0.2.55 (`fix: find podfetch episodes and stop skipping unconfigured
podcasts`). That commit corrected the engine's copy of this pattern in
`pkg/adremoval`; these two instances were deliberately left alone because
fixing them naively changes download behaviour. Neither is urgent: once the
engine writes a `podcast.json` on its first real run, every reader sees a
real file and they all agree again. They matter for a podcast folder that
has not been through ad removal yet.

---

## Issue 1 — The CLI and TUI bridges read podcast config with a zero-value default

**Where**

- `pkg/cli/bridge.go` — `loadPodcastConfig`
- `pkg/tui/bridge.go` — `loadPodcastConfig`

```go
func loadPodcastConfig(dir string) PodcastConfig {
	return config.LoadPodcastConfig(dir, config.PodcastConfig{})
}
```

**What is wrong**

The zero value is not a neutral default. `LoadPodcastConfig` hands the default
to `normalizeLoadedPodcastConfig`, which copies `def.AdRemoval` into any
config that does not set the field — including the case where no
`podcast.json` exists at all. `NormalizeAdRemovalMode("")` returns
`AdRemovalNone`, so "no config" and "config written before the `ad_removal`
key existed" both silently mean "never remove ads from this podcast".

Everywhere else in the tree the fallback is the real default,
`config.DefaultPodcastConfig(...)`, which yields `ad_removal: "all"` and
honours the app-level `default_ad_policy`. `pkg/podcast` uses it at eight
call sites; these two bridges are the outliers.

**Why it matters**

`pkg/adremoval` now treats an unconfigured podcast as `all`, so the engine
will process a podcast that `abs info status` and the TUI still present as
excluded. The two disagree until a `podcast.json` exists.

**Proposed fix**

Use `config.DefaultPodcastConfig` as the fallback in both bridges. Passing the
app config rather than `nil` would also honour `default_ad_policy`, but
neither bridge has it in scope today, so it would have to be threaded through
(`pkg/cli/info_status.go` and `pkg/tui/tui_data.go` are the relevant callers).

**Why this was not done alongside the engine fix**

`normalizeLoadedPodcastConfig` fills in `download_policy` and `download_k`
from the same default, and both bridges pair `loadPodcastConfig` with
`savePodcastConfig` for editing. Today a config missing `download_policy`
normalizes to `DownloadPolicyNone` (auto-download off); with
`DefaultPodcastConfig` it would become `latest`/`k=3` — auto-download **on**
— and the TUI would then persist that on the next save. Switching the default
therefore silently enables downloads for any podcast whose config omits the
key, which is a larger behaviour change than the ad-removal fix called for.

Any fix should either scope the default to the ad-removal field only, or
change the download default deliberately and say so in the changelog.

## Issue 2 — `abs info status` compares the raw ad-removal mode

**Where**

`pkg/cli/info_status.go:65`

```go
podCfg := loadPodcastConfig(podPath)
if podCfg.AdRemoval == AdRemovalNone {
	continue
}
filtered := filterMP3FilesByPodcastConfig(mp3s, podPath, podCfg)
```

**What is wrong**

`podCfg.AdRemoval` is the raw field, so the guard only catches the literal
string `"none"`. An empty mode — the zero-value default from Issue 1 — slips
past it and is normalized to `none` one step later inside
`filterMP3FilesByPodcastConfig` → `podcast.FilterByAdRemovalPolicy`, which
returns nothing.

This is the same double fault that hid the podfetch discovery bug: the guard
that was supposed to explain the skip never fires, and the episodes disappear
silently at the next step instead.

**Why it matters**

Today the end result is the same either way — zero episodes — so this is
latent rather than user-visible. It matters because the early guard is the
only place that could report *why* a podcast was excluded, and because the
counters above it (`podcastsCount`, `totalEpisodes`) still include a podcast
that contributes nothing, which makes the status output internally
inconsistent.

**Proposed fix**

Compare the normalized mode:

```go
if config.NormalizeAdRemovalMode(podCfg.AdRemoval) == AdRemovalNone {
	continue
}
```

This mirrors what `pkg/adremoval/batch_proc.go` now does. On its own it does
not change any output; it becomes load-bearing once Issue 1 is fixed, and it
makes the exclusion explicit at the point where it is decided.

---

## Resolution

Resolved in 0.5.6:
1. Introduced `config.DefaultDiscoveredPodcastConfig(appCfg)` in `pkg/config/podcast.go`, which defaults `AdRemoval` to `"all"` (honoring app config) while keeping `DownloadPolicy` as `"none"` (so unconfigured local podcasts are eligible for ad removal without accidentally enabling auto-downloads).
2. Updated `pkg/cli/info_status.go`, `pkg/cli/info_list.go`, and `pkg/tui/tui_data.go` to use `DefaultDiscoveredPodcastConfig`.
3. Updated `pkg/cli/info_status.go` to compare `config.NormalizeAdRemovalMode(podCfg.AdRemoval)` in both `renderLocalSummary` and `renderLocalDiskPodcastStatus`.
